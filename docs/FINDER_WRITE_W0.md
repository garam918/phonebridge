## 방법

> 2026-10-22 W2에서 관찰 모드는 실제 쓰기 경로로 대체되어 코드에서 제거됐다(D35). 아래는 당시 기록.

- 확장에 **진단용 쓰기 관찰 모드**(`PhoneBridgeFinder/WriteObservation.swift`)를 추가했다. 조건: 앱 실행 인자 `-diagnostics.finderWriteObservation YES`이고 **가상 기기 볼륨일 때만** 켜진다. UI에는 없고 저장되지 않는다.
- 관찰 모드의 쓰기는 확장 프로세스의 임시 폴더에만 반영된다. 앱(IPC)·MTP·실제 기기로는 아무것도 가지 않는다(기존 가상 기기 파일에 쓰면 원본을 읽어 로컬 사본을 만든 뒤 사본에 쓴다). 볼륨이 해제되면 사라진다.
- 모든 FSKit 호출(create, open/close, write, setattr, rename, remove, preallocate, synchronize)을 `w0` 로그 범주로 기록했다. 원본 기록은 `docs/w0-traces/*.txt`.
- 같은 시각 휴대전화 볼륨은 그대로 읽기 전용(`dr-xr-xr-x`)이었다.
- 실험용 프로브: 이름에 `W0-FAIL`이 들어간 파일은 마지막 닫기에 `EIO`, `W0-SLOW`는 닫기 응답을 20초 늦춘다(관찰 모드에서만).

## 설계에 반영할 결론

1. **커밋 시점 = 쓰기 핸들의 마지막 close.** 닫기 오류는 `cp`와 Finder 모두 사용자에게 드러나고 Finder는 부분 파일을 지운다 → 계획의 "닫기 응답에 업로드 결과 전달"이 유효. 같은 파일의 close가 두 번 오는 경우가 있어 **커밋은 변경이 있을 때 한 번만**(멱등).
2. **빈 자리표시 파일을 기기에 올리지 않는다.** Finder는 복사마다 0바이트 파일을 만들고 곧 지운다. 새로 만든 0바이트 파일은 로컬 대기 항목으로 두고, 그 사이 지워지면 MTP 호출 없이 끝낸다. 0바이트로 남는 파일(예: `touch`)은 짧은 대기(2초) 뒤 기기에 만든다.
3. **close 뒤에 오는 시각·권한 설정은 받아들이고 무시한다.** 기기 파일 시각은 업로드 시점 값.
4. **삭제는 지연 삭제로 원본을 보호한다.** Finder "대치"는 원본을 먼저 지운다. 파일 `remove`는 즉시 목록에서 숨기고 기기에서는 숨김 백업 이름으로 바꿔 두었다가, 같은 자리의 새 파일 커밋이 성공하거나 30초가 지나면 실제로 삭제한다. 새 파일 커밋이 실패하면 원본을 되살린다(D33).
5. **`._*`·`.DS_Store`는 기기에 올리지 않는다.** 호출의 60–95%가 이 파일들이다. 두 방법 중 W2에서 고른다: (a) 그림자 항목(계획 원안) (b) 확장 속성을 확장 메모리에 직접 지원해 커널이 `._` 파일을 만들지 않게 함. (b)가 호출 수·이름 처리 면에서 유리해 보이며 W2에서 먼저 시도.
6. **열린 파일의 rename을 지원한다.** 원자적 저장은 쓰는 중인 임시 파일을 최종 이름으로 바꾼 뒤 닫는다. 대기 항목의 rename은 로컬에서만 처리하고, close 때 최종 이름으로 커밋(기존 파일이 있으면 교체 순서).
7. **다른 폴더로의 rename = MTP 이동.** Finder 이동과 `replaceItemAt` 모두 사용. `canMoveNatively` 기기는 MoveObject, 아니면 `EXDEV` — Finder가 복사+삭제로 바꾸는지는 W2에서 확인.
8. **기존 파일 수정은 원본 전체를 먼저 받아 와야 한다.** 덧붙이기도 페이지 단위 재기록이라 부분 업로드가 불가능(MTP 기본 기능 기준). 큰 파일 수정은 전체 다운로드 + 전체 업로드 비용(W6에서 개선 검토).
9. **희소 파일·잘라내기·늘리기**가 실제로 오므로 로컬 버퍼는 크기 변경을 그대로 지원해야 한다.
10. 남은 확인: 수 분 걸리는 close(대용량 업로드)에서 Finder·FSKit 시간 제한 여부 — W2에서 5 GB로 확인.
