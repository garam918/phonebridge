# 검토: 업로드 중 탐색 대기(27.5초)와 실기기 루트 이동 (2026-10-22)

상태: 검토 후 사용자 승인으로 **A 구현·실기기 확인 완료**(2026-10-23, 결과는 맨 아래와 DECISIONS V12). 근거: 이 저장소 코드, libmtp 1.1.23 헤더, AOSP `frameworks/av/media/mtp/MtpServer.cpp`(main), W5 실측(V11).

## 1. 업로드 중 탐색 대기

### 원인
- **기기 쪽**: Android `MtpServer`는 요청을 하나씩 처리한다(`run()` 루프에서 한 트랜잭션이 끝나야 다음 요청). 한 트랜잭션 안에서 다른 요청이 끼어들 수 없다.
- **앱 쪽**: `MTPDeviceSession`은 기기별 직렬 실행기(actor) 위에서 MTP 호출을 하나씩 실행한다. 업로드는 `LIBMTP_Send_File_From_File_Descriptor` **한 번의 호출**(SendObjectInfo + SendObject 데이터 단계 전체)이라, 끝날 때까지 목록·읽기 요청이 대기열에서 기다린다.
- 결과: 1 GiB(31초 업로드) 중 목록 요청이 최대 27.5초 대기(V11). 대기 시간 ≈ 남은 업로드 시간.

### 선택지

| 안 | 내용 | 예상 효과 | 비용·위험 |
|---|---|---|---|
| **A. 조각 업로드(권장)** | 빈 객체를 만든 뒤(현재도 0바이트 업로드는 실기기에서 성공) Android 편집 확장으로 `BeginEditObject` → `SendPartialObject`(예: 16 MiB씩, 조각마다 별도 세션 호출) → `EndEditObject`. 조각 사이에 대기 중인 목록·읽기 요청이 실행된다 | 최악 대기 ≈ 조각 하나 시간(16 MiB ÷ 약 33 MiB/s ≈ 0.5초) | 편집 확장이 있는 기기만(S25는 caps에 있음, 없으면 지금 방식). 조각마다 트랜잭션이 늘어 속도가 조금 떨어질 수 있음(실측 필요). AOSP: `SendPartialObject`는 편집 중인 객체에만, 시작 위치가 현재 크기 이하일 때만 허용 → 앞에서부터 순서대로 보내면 맞음. 실패 시 빈/부분 객체는 기존 스테이징 이름이라 지금의 정리·일지 규칙이 그대로 적용됨. 앱 창 전송(TransferManager)도 같은 경로라 함께 좋아짐 |
| B. 목록 캐시로 응답 | 업로드 중에는 이미 본 폴더 목록을 캐시에서 바로 준다 | 본 적 있는 폴더만 해결, 새 폴더·파일 읽기는 여전히 대기 | 목록이 잠시 오래된 내용일 수 있음 |
| C. 그대로 두고 안내 | 문구로 "큰 파일을 올리는 동안 같은 기기 탐색이 느려질 수 있음" 안내 | 없음 | 없음 |

A가 근본 해결이다. B는 A와 함께 쓸 수 있는 보조책이지만 지금은 필요성이 낮다.

### A를 적용할 경우 구현 범위
1. 브리지: `pb_begin_edit`, `pb_send_partial(handle, offset, buffer)`, `pb_end_edit`, `pb_truncate`(libmtp 1.1.23에 모두 있음).
2. `MTPDeviceSession`: 업로드를 "빈 객체 생성 → 편집 시작 → 조각 반복(조각마다 actor 호출이 끝나 다른 요청이 끼어들 수 있음) → 편집 끝"으로. 진행률·취소는 조각 단위. 실패 시 편집 종료를 시도하고 상위(스테이징 정리)가 객체를 지움.
3. 적용 조건: `PB_CAP_EDIT_OBJECTS` + 일정 크기 이상(예: 32 MiB). 아니면 기존 한 번 전송.
4. 시험: Mock 백엔드에 편집 확장 시뮬레이션, 조각 사이 목록 요청이 끼어드는지(대기 시간 상한) 단위 테스트.
5. 실기기 측정(승인 필요, 테스트 폴더 안): 1 GiB 업로드 속도·해시, 업로드 중 목록 최대 대기, 조각 중 분리 시 정리.

## 2. 실기기 루트 이동

### 코드 기준 결론
AOSP `MtpServer.cpp`:
- `doSendObjectInfo`: `if (parent == MTP_PARENT_ROOT)`(0xFFFFFFFF)만 루트. 0은 핸들로 찾다가 실패 → W5에서 본 2009 오류와 일치(D39에서 수정).
- `doMoveObject`, `doCopyObject`: **`if (parent == 0)`이 루트**. 0xFFFFFFFF는 핸들로 찾다가 실패한다.
- PhoneBridge 브리지는 이동·복사에서 루트를 0으로 보낸다 → **AOSP와 일치**. 삼성이 이 부분을 바꾸지 않았다면 동작해야 한다.

### 남은 위험
삼성 펌웨어가 AOSP와 다를 가능성, 그리고 지금까지 실기기에서 루트로/루트에서 이동을 한 번도 하지 않았다는 점.

### 실기기 확인 방법(승인 필요)
루트에 무언가를 잠시 두어야 하므로 지금의 범위 제한(테스트 폴더 안만)을 벗어난다. 안전하게 하려면:
1. 범위 제한에 예외 하나만 추가: **이름이 "PhoneBridge W5 테스트"로 시작하는 루트 파일**만 허용(진단 실행 인자에서만).
2. 테스트 폴더 안에 작은 파일 "PhoneBridge W5 테스트 루트이동.txt"를 만든다 → 루트로 이동 → 해시 확인 → 다시 테스트 폴더로 이동 → 해시 확인.
3. 루트에 머무는 시간은 몇 초이며, 다른 루트 항목은 읽지도 건드리지도 않는다.

## 3. 결과 (2026-10-23 00:00–00:11, SM-S937N, 테스트 폴더 안 + 루트 파일 1개)

- **조각 업로드(A) 구현**: `MTPDeviceFileSystem`이 `canUploadInChunks`(편집 확장 + SendPartialObject)이고 32 MiB 이상이면 빈 객체 생성 → BeginEditObject → 16 MiB씩 SendPartialObject(조각마다 별도 세션 작업) → EndEditObject. 실패 시 편집을 닫고 부분 객체는 호출자(스테이징 정리)가 지운다. 앱 창 전송도 같은 경로.
- **탐색 대기**: 1 GiB Finder 복사 중 다른 폴더 목록 + 파일 4 KB 읽기의 최악 대기 **27.5초 → 0.9–1.9초**(평균 약 0.6초). 1 GiB 전체 33–35초(이전 37.5초), 업로드 31–33초로 속도 손실 없음.
- **발견·수정한 문제**: 진단용 숨김 객체 표시를 켠 상태에서 조각 업로드 중인 임시 객체(크기가 30초 동안 자람)가 Finder 항목으로 캐시되어, 업로드 직후 같은 객체의 크기가 0으로 보이고 읽기가 틀린 경우가 2회 있었다(7회 중 1회 재현). **기기의 데이터는 매번 정상**(새 마운트에서 해시 일치). 숨김 객체 표시를 끈 일반 상태에서는 4/4 정상, 이름 변경 직후 기기 보고 크기 80회 표본 모두 정상. → 확장은 기본적으로 임시 객체를 목록에서 숨기고, 마운트 URL에 `&staging=1`이 있을 때만(잔여물 확인용 별도 마운트) 보이게 수정. 수정 후 3/3 정상.
- **루트 이동**: 테스트 폴더의 "PhoneBridge W5 테스트 루트이동.txt"를 루트로 이동 → 해시 일치 → 다시 테스트 폴더로 → 해시 일치. 새 마운트에서 루트에 남은 것 없음. **MoveObject의 루트 = 0이 삼성 기기에서도 맞음**(AOSP와 일치). 다른 이름으로 루트 이동은 범위 제한이 거부.
