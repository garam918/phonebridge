## 1. 전제와 원칙

| 원칙 | 내용 |
|---|---|
| MTP는 POSIX 쓰기가 아니다 | MTP의 기본 쓰기는 "객체 전체를 새로 보내기"(SendObjectInfo + SendObject)뿐이다. 임의 위치 쓰기·잘라내기·덧붙이기는 표준에 없다. Android 확장(BeginEditObject / SendPartialObject / TruncateObject / EndEditObject, `PB_CAP_EDIT_OBJECTS`)이 있는 기기도 있지만(SM-S937N은 caps=63으로 지원 보고), **1차 구현은 이 확장에 의존하지 않는다**(§9 선택 단계). |
| 임의 위치 쓰기는 Mac 쪽 로컬 파일에서만 | Finder가 보내는 `write(offset:)`·`truncate`는 Mac의 임시 파일에 반영하고, 파일이 닫힐 때 기기에 **전체 내용을 한 번에** 올린다. |
| MTP 세션은 앱만 가진다 | 확장은 지금처럼 libmtp 없이 IPC만 쓴다. 업로드·이름 변경·삭제는 앱의 DeviceBroker 세션과 직렬 큐를 거친다. |
| 원본은 잃지 않는다 | 기존 TransferManager 규칙(D16, D26) 재사용: 숨김 스테이징 이름으로 업로드 → 크기 검증 → 기존 파일을 백업 이름으로 → 스테이징을 최종 이름으로 → 백업 삭제. 중간 실패 시 백업 복원, 복원도 실패하면 백업을 남긴다. |
| 기본은 꺼짐 | 설정 › Finder › "Finder에서 쓰기 허용(실험적)", 기본 꺼짐. 꺼져 있으면 현재와 똑같이 읽기 전용(EROFS)이다. 저장소가 읽기 전용이면 켜도 읽기 전용이다. |

## 2. 데이터 경로

```
Finder (copy/new folder/rename/delete)
  └─ PhoneBridgeFinder.appex
       ├─ 쓰기 오버레이: 아직 기기에 없는 항목(생성 중 파일), 이름 변경·삭제 대기, 임시 ID
       ├─ 쓰기 버퍼: App Group 컨테이너/FinderWrites/<uuid>.buffer  (임의 위치 쓰기·잘라내기)
       └─ IPC v2 ──► PhoneBridge.app
                       MTPFileRepository (쓰기 메서드 추가)
                         └─ FinderWriteCoordinator: 볼륨당 직렬, TransferManager와 같은 안전 규칙
                              └─ DeviceFileSystem.upload / createFolder / rename / move / delete
```

- 버퍼 파일을 **App Group 컨테이너**에 두면 앱이 경로만 받아 그대로 `upload(from:)`할 수 있다. 소켓으로 대용량을 스트리밍할 필요가 없다(현재 프레임 최대 64 MB 제한과 무관).
- 커밋 시점: 쓰기용으로 열린 핸들이 모두 닫힐 때(`closeItem`) 또는 `synchronize`. 닫기 응답은 업로드·검증이 끝난 뒤에 보낸다(실패하면 오류로 응답).

## 3. Finder 동작 → MTP 매핑

| Finder/POSIX 동작 | 처리 | 기기 쪽 결과 |
|---|---|---|
| 새 폴더(`mkdir`) | 즉시 IPC `createFolder` | 폴더 생성 |
| 새 파일 생성(`create`) | 오버레이에 임시 항목(임시 ID, 크기 0) + 빈 버퍼 | 닫힐 때까지 기기에는 없음. **0바이트로 닫힌 새 파일은 2초 대기 후 생성**(Finder의 자리표시 파일은 곧 지워지므로 기기 호출 없음, W0) |
| `write(offset)` / `truncate` | 버퍼 파일에 반영 | 없음 |
| 기존 파일을 쓰기로 열기(덮어쓰기·부분 수정) | 처음 쓰기 전에 원본을 버퍼로 내려받음(잘라내기로 시작하면 생략) | 없음 |
| 닫기(마지막 핸들) / `fsync` | 커밋: 스테이징 업로드 → 크기 검증 → 교체. 변경이 있을 때 한 번만(close가 두 번 올 수 있음, W0) | 새 파일 또는 교체 |
| 쓰는 중인 파일의 rename(원자적 저장) | 대기 항목이면 로컬에서만 이름 변경, close 때 최종 이름으로 커밋(대상이 있으면 교체 순서) | 최종 이름으로 한 번 업로드 |
| 같은 폴더 안 이름 변경 | MTP rename. 대상 이름이 있으면 백업 순서로 교체 | 이름 변경 |
| 다른 폴더로 이동(같은 저장소) | `canMoveNatively`면 MoveObject, 아니면 `EXDEV`(Finder가 복사+삭제로 처리하는지 W7에서 확인) | 이동 |
| 파일 삭제(`unlink`) | **지연 삭제(D33)**: 목록에서 즉시 숨기고 기기에서는 숨김 백업 이름으로 변경. 같은 자리의 새 파일 커밋 성공 또는 30초 경과 시 실제 삭제, 새 파일 커밋 실패 시 원본 복원 | Finder "대치"가 원본을 먼저 지워도 새 파일 검증 전까지 원본 유지(W0) |
| 빈 폴더 삭제(`rmdir`) | MTP delete. 비지 않은 폴더는 `ENOTEMPTY`(Finder·`rm -r`가 안쪽부터 지움, W0) | 삭제 |
| 수정 시각·권한·플래그 설정 | 받아들이고 무시. Finder는 이 설정을 **close 뒤에** 보낸다(W0) | 기기가 정한 시각(업로드 시점) |
| 크기 변경(`truncate`, 늘리기) | 버퍼에 반영. Finder는 희소 파일을 "크기 늘리기 + 끝부분만 쓰기"로 복사(W0) | close 때 반영 |
| 확장 속성(xattr) | W2에서 결정: 확장 메모리에 직접 보관(커널이 `._` 파일을 만들지 않음, 우선 시도) 또는 `ENOTSUP` + `._` 그림자 항목 | 기기에 저장 안 함 |
| 하드/심볼릭 링크 | `ENOTSUP` | 없음 |
| `._*`(AppleDouble), `.DS_Store`, `.Trashes`, `.fseventsd`, `.Spotlight-V100` | **기기에 올리지 않음.** 확장 메모리의 "그림자 항목"으로만 유지(용량 상한, 마운트 해제 시 폐기) | 없음 |

## 4. 일관성과 동시성

- 볼륨당 쓰기 커밋은 직렬. 앱 UI의 전송 큐와 같은 기기 세션을 쓰므로 MTP 호출은 지금처럼 직렬화된다.
- 커밋 후: 확장의 디렉터리 캐시(3초)와 앱의 읽기 캐시에서 해당 폴더·객체를 무효화. 앱 탐색기 화면도 같은 폴더를 다시 읽는다.
- 앱 UI와 Finder가 같은 이름을 동시에 만들면 나중 쪽이 충돌(`EEXIST`) 처리. 앱 전송 큐의 충돌 시트와 섞지 않는다.
- 업로드 전 공간 확인: 기기 여유 공간(`ENOSPC`), Mac 쪽 버퍼 공간(App Group 볼륨 여유). 5 GB 파일을 복사하면 Mac에도 5 GB 임시 공간이 잠시 필요하다.

## 5. 실패 처리

| 상황 | 처리 |
|---|---|
| 업로드 중 케이블 분리 | 닫기에 `ENXIO`/`EIO` 응답 → Finder 오류 표시. 기기의 원본은 그대로(교체 전이므로). 다음 세션에서 남은 스테이징 객체(`FileNameRules` 임시 이름) 정리 |
| 크기 검증 불일치 | 스테이징 삭제, 원본 유지, `EIO` |
| 교체 중 실패 | 백업 복원. 복원 실패 시 백업 이름을 남기고 앱 알림으로 위치 안내 |
| 커밋 실패한 버퍼 | 즉시 지우지 않고 "Finder에서 저장하지 못한 파일"로 앱에 알림 → 사용자가 Mac에 저장하거나 버릴 수 있게 함(데이터를 조용히 잃지 않기 위함). 마운트 해제·앱 재시작 후에도 남음 |
| 앱이 꺼져 있음 | 지금처럼 IPC 실패 → `ENXIO`. 쓰기 없음 |

## 6. IPC 프로토콜 v2

`FinderIPC.protocolVersion = 2`. 확장과 앱의 버전이 다르면 쓰기를 거부하고 읽기만 허용.

| 요청 | 응답 |
|---|---|
| `createFolder(address, parent, name)` | `entry` |
| `commitFile(address, parent, name, replacing: objectID?, bufferPath, size, modified)` | `entry`(새 객체 ID) |
| `rename(address, object, newName, replacing: objectID?)` | `entry` |
| `move(address, object, newParent)` | `entry` 또는 `EXDEV` |
| `delete(address, object)` | 성공 |
| `capabilities(address)` | 쓰기 허용 여부, 이동·이름 변경 지원 |

`bufferPath`는 App Group 컨테이너 안이어야 하며 앱이 경로를 검증한다(경로 탈출 차단).

## 9. 위험과 확인이 필요한 점

1. ~~닫기 오류를 Finder가 확인하는지~~ **W0 확인**: `cp`는 EIO로 실패 종료, Finder는 -36 오류를 띄우고 부분 파일을 지운다. 다른 앱이 무시할 가능성에 대비해 앱 알림(§5)은 유지.
2. **닫기가 오래 걸림**: 20초 지연은 `cp`·Finder 모두 정상 대기(W0). 수 분(5 GB 업로드) 지연은 W2에서 확인. 문제가 되면 순차 쓰기일 때 쓰는 도중에 미리 올리는 방식을 검토.
3. **수정 시각**: 업로드 뒤 Finder가 정하는 시각은 반영되지 않을 수 있다(기기마다 다름).
4. **앱의 "안전한 저장"(TextEdit 등)**: 임시 파일 + 교체(`RENAME_SWAP`)를 쓴다. 교체는 `ENOTSUP`로 거절해 일반 이름 변경으로 넘어가게 하고, 1차 범위는 Finder 파일 관리로 한정한다(문서 편집 저장은 최선 노력, 별도 검증).
5. **휴지통**: 기기에 `.Trashes`를 만들지 않으므로 Finder는 "즉시 삭제" 경고를 띄운다. 실수로 지울 위험이 있어 쓰기 허용 기본값을 꺼짐으로 둔다.
6. **Mac 임시 공간**: 대용량 복사는 Mac 디스크도 같은 크기만큼 일시 사용.

## 10. 결정이 필요한 점 (사용자)

- 쓰기 허용 기본값: **꺼짐 + "실험적" 표시**(권장)
- 삭제: Finder 기본 동작(즉시 영구 삭제 + 경고) 유지(권장) / 기기에 휴지통 폴더를 따로 두기
- 실기기 검증 위치: 휴대전화의 전용 테스트 폴더 하나로 제한(권장)
